# 10 — ارتباط با KavoshUI

قواعد: UI-1…3

## تقسیم مسئولیت
| موضوع | مرجع |
|---|---|
| تصمیم‌های آغاز معماری، روش‌های مهندسی مصوب، روند کار، CI، انتشار و عامل‌ها | **KavoshStart** |
| ظاهر، کامپوننت، تعامل، دسترس‌پذیری، RTL، اعداد/تاریخ فارسی در UI | **KavoshUI** |
| مدل و معنای کسب‌وکار، داده و API اختصاصی و تنظیم اتصال‌ها | خود پروژه |

## قواعد مصرف
1. `ui.kavoshui` در مانیفست نسخه‌ی **دقیق** را پین می‌کند (نه `latest`، نه `^`).
2. کامپوننت‌ها از بسته‌های نسخه‌دار KavoshUI مصرف می‌شوند، به همان روشی که KavoshUI در README و `CONSUMER_CONFORMANCE_STANDARD_FA.md` خودش تعریف می‌کند. کپی کد کامپوننت در پروژه ممنوع؛ کمبود = Issue در KavoshUI.
3. استثنای استفاده از KavoshUI برای یک پروژه در ADR همان پروژه ثبت می‌شود: چرایی، محدوده، طراحی RTL، دسترس‌پذیری، مالکیت به‌روزرسانی و معادل‌های آزمون. کپی کد KavoshUI مجاز نمی‌شود.
4. ارتقای KavoshUI = PR جدا `chore(ui): upgrade KavoshUI to vX.Y.Z`. شواهد رندر RTL/موبایل/تم تیره برای تغییرات بصری یا تعاملی لازم است؛ تغییر غیرنمایشیِ API یا متادیتا screenshot نمی‌خواهد.
5. عامل پیش از هر کار UI این اسناد KavoshUI را می‌خواند: `AGENTS.md`، `docs/foundations/DESIGN_STANDARD_FA.md`، `docs/foundations/COMPONENT_SELECTION_STANDARD_FA.md`، `docs/architecture/CONSUMER_CONFORMANCE_STANDARD_FA.md` — و **نه** همه‌ی 91 سند.

## یک گفت‌وگوی آغاز، نه دو پرسشنامهٔ مستقل

قابلیت و روش اتصال در intake کاوش‌استارت تعیین می‌شود؛ قرارداد نمایش و تعامل از KavoshUI می‌آید. بخش G پرسشنامه، تصمیم‌های قطعی را در `PROJECT.md#architecture-decisions` ثبت می‌کند. این جدول منبع دوم مقادیر manifest یا tracker وضعیت نیست. در ادامهٔ کار، پاسخ‌های همان دامنه دوباره پرسیده نشوند.

لایسنس محصول، احراز هویت، جداسازی داده و رفتار قطع ارتباط پیش از پیاده‌سازی وابسته مشخص شوند. KavoshUI فقط وضعیت و تعامل مرتبط را نمایش می‌دهد؛ نام سرویس لایسنس یا مخفی‌کردن دکمه جای قرارداد اعتبارسنجی و مجوز کاربر نیست. مدیریت حق استفاده از فونت با مالک تعیین‌شده باقی می‌ماند و با لایسنس محصول یکی نیست.

برای `ui.kind=none` کار UI ایجاد نمی‌شود. در پروژهٔ دارای UI، دستگاه، زبان، تقویم، فونت، چاپ، جست‌وجو و راهنما بر اساس نیاز انتخاب شوند. مثال یک محصول، قابلیت اجباری برای همهٔ محصولات نیست. اگر قرارداد نسخهٔ منتخب KavoshUI قابلیت یا زیرساخت اضافی می‌خواهد، ناسازگاری را در همان تصمیم اولیه آشکار کنید؛ نه بی‌اجازه قابلیت بسازید، نه با عبارت «لازم نیست» یک gate موجود را دور بزنید. اصلاح قرارداد یا استثنای مجاز، مسیر بازبینی‌شدهٔ خودش را دارد.

معیارهای پذیرش و شواهد هر قابلیت همراه همان قابلیت طراحی و جمع‌آوری شوند. آزمون کتابخانه، آزمون اتصال و پذیرش محصول ادعاهای جدا هستند؛ هیچ‌یک جای دیگری را نمی‌گیرد و آزمون مشترک معتبر نباید برای هر ردیف الزام دوباره ساخته شود.

## نکته برای خود KavoshUI
KavoshUI یک پروژه‌ی T1 (کتابخانه‌ی مصرف‌شده توسط دیگران) است و باید KavoshStart را بپذیرد. ممیزی آن باید فقط داده‌های خود KavoshUI را مبنا قرار دهد؛ پذیرش آن در [adoption/ADOPTION.md](../adoption/ADOPTION.md) پیشنهاد شده است.
