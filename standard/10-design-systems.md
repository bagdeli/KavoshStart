# 10 — Design System انتخابی هر پروژه

قواعد: UI-1…3 و TP-1/2.

## مرز عمومی

KavoshStart نام مخزن، بسته، URL، نسخه، تصاویر یا اطلاعات runtime مصرف‌کنندگان private را منتشر نمی‌کند. استاندارد صرفاً قرارداد عمومی انتخاب، پین دقیق، حقوق استفاده، RTL، دسترس‌پذیری و شواهد مشاهده را تعریف می‌کند.

## قرارداد مصرف

1. برای پروژهٔ دارای UI، اگر بستهٔ Design System انتخاب شد، `ui.designSystem` باید `package` و `version` دقیق آن را داشته باشد. UI سفارشیِ انتخاب‌شدهٔ مالک‌محور بدون بسته و بدون ADR اضافی مطابق UI-1 مجاز است و نبود pin هشدار است؛ فرایند تیمیِ انتخاب‌شده (`review.teamProcess=true`) برای مسیر بدون بسته `ui.exceptionADR` مصوب می‌خواهد. در هر دو حالت RTL، دسترس‌پذیری و حقوق استفاده لازم‌اند و انتخاب واقعی در مخزن مصرف‌کننده باقی می‌ماند.
2. بلوغ، TCO، امنیت، پشتیبانی، compatibility و License/NOTICE/فونت/asset طبق TP-1/2 ارزیابی شوند؛ هیچ ارائه‌دهنده یا فریم‌ورکی در Core اجباری نیست.
3. بسته از dependency نسخه‌دارِ مصوب مصرف می‌شود. کپی‌کردن کد component به‌جای استفاده از package بدون حق و دلیل معتبر پیش‌فرض نیست. سازگاری API، UI consumer و آزمون مرتبط با هم بررسی شوند.
4. ارتقا در PR مستقل است؛ رندر/تعامل واقعی با مقایسهٔ ماشینیِ معتبر یا مشاهده و قضاوت واقعیِ خود مالک روی منبع/نسخهٔ صحیح بررسی می‌شود. بازبین انسانی دوم فقط در فرایندِ صریحاً انتخاب‌شده لازم است؛ لینک، screenshot بی‌منبع یا ادعای agent به‌تنهایی کفایت نمی‌کند.
5. برای مسیر بدون بسته، scope، مالکیت، RTL، accessibility، روش بررسی متناسب و هزینهٔ نگهداری در تصمیم/Issue موجود ثبت شود؛ فقط فرایند تیمیِ انتخاب‌شده به ADR استثنا نیاز دارد. نبود بسته مجوز نقض حقوق اجزای شخص ثالث نیست.
6. در پروژهٔ فاقد UI، کار یا مدرک UI مصنوعی ایجاد نمی‌شود. انتخاب و شواهد حقیقی باید با سطح visibility همان مصرف‌کننده نگهداری شوند.

اعتبارسنجی package، آزمون integration و پذیرش محصول شواهدی مستقل‌اند. بدون دادهٔ واقعی نمی‌توان ادعای انطباق مصرف‌کننده داشت.

طراحی صفحه/جریان کارِ **تغییر انتخاب‌شده** متعلق به همان Product و Issue/Spec/plan موجود آن است، نه به بستهٔ UI یا KavoshStart: actor/task، مسیر و navigation، محتوای لازم و field/action/setting، مالک خواندن/نوشتن داده و مرز مجوز، stateهای موفق/خطا/عدم‌دسترسی/خالی و قرارداد layout/component نسخهٔ انتخابی را تا حد اثر تغییر روشن کنید. برای رفتار مشترک به قرارداد موجود ارجاع دهید و فقط تفاوت‌های صفحه را بنویسید. تصمیم حل‌نشده فقط کار وابسته را متوقف می‌کند؛ پایان طراحی دامنه‌دار با نصب بسته، مشاهدهٔ رندر، پذیرش واقعی محصول و Release یکسان نیست. انتخاب فنیِ تفویض‌شده فقط در محدودهٔ مصوب ثبت می‌شود و به معنای رؤیت یا پذیرش تصویریِ انجام‌نشده توسط مالک نیست؛ برای تغییر بدون UI یا اصلاح کوچک، مستندات/گیت جداگانه نسازید.

## انتخاب روش طراحی و مدرک برای دامنهٔ موردنیاز — پیشنهاد، نه الزام همگانی

**اصل قابل‌تعمیم:** هر Product بر اساس ماهیت کار، ریسک و تصمیم‌های واقعی خودش مشخص می‌کند که آیا مرجع تصویری تازه لازم است و چه کسی/چه روشی آن را بررسی می‌کند. KavoshStart **صاحب ترتیب و ثبت تصمیم** است، نه صاحب UI، منو، مجوز یا ساخت اجباری تصویر و فایل برای همهٔ محصولات. این بند هنوز Rule/Schema/CI gate منتشرشده نیست.

| وضعیت واقعی | مسیر متناسب |
| --- | --- |
| بدون UI، کار Backend یا تغییر مستقل از ظاهر | فقط آزمون و شاهد صاحب همان تغییر؛ بدون ScreenSpec، تصویر یا مرحله تصویب اضافه |
| تغییر محدود UI با قرارداد روشن | همان Issue/Spec و آزمون/بازبینی مرتبط؛ UI-2 برای رگرسیون اجراشده بازبینی انسانی واقعی **یا** مقایسهٔ معتبر ماشینی را می‌پذیرد |
| طراحی/بازطراحی مؤثر که محصول برای آن Spec یا مرجع دیداری انتخاب می‌کند | تا حد دامنهٔ **متأثر** actor/task، صفحه/حالت، navigation، read/write owner و permission روشن شود؛ از قرارداد موجود و جزء نسخه‌دار استفاده گردد |
| Product با فرایند **صریحاً انتخاب‌شدهٔ reference-first و owner-approved image** | برنامه و ScreenSpec همان دامنه از پیش روشن می‌شود؛ تصویر/مجموعهٔ مشخص پس از QA واقعاً به صاحب اختیار نشان داده شده و تصمیم دربارهٔ همان نسخه ثبت می‌شود؛ اجرای وابسته از مرجع ردشده آغاز نمی‌شود |

**مرز کیفیت:** اگر تصویری به‌عنوان شاهد یا مرجع استفاده می‌شود، باید اصل محتوای بررسی‌شده، source/version، context و شاهد QA متناسب قابل بازیابی باشد؛ file extension یا hash بدون بایت کافی نیست. نوع فایل تابع خروجی است: raster lossless برای baseline پیکسلی انتخاب‌شده، SVG برای بردارِ واقعاً موردنیاز با بررسی renderer/font؛ هیچ دستور سراسریِ «همه چیز PNG»، «دو فایل برای هر صفحه» یا «تصویب انسانی تک‌تک تغییرها» وجود ندارد. ثبت منبع/recipe دوم تنها وقتی لازم است که منبع اصلی برای بازتولید قابل بازیابی نیست و ارزش واقعی دارد.

**ادامه و تغییر:** از تصمیم‌های معتبر موجود بازاستفاده شود؛ تصویر/مرجع ساخته‌نشده نباید تاییدشده یا قابلیت اجراشده معرفی شود؛ تغییر مؤثر در نقش/داده/منو/فونت/جزء فقط **خروجی‌ها و تست‌های متأثر** را بازمی‌گشاید. اگر بنیاد مشترکی واقعاً همه صفحات را تحت تأثیر می‌گذارد، همان دامنه وسیع بررسی شود، نه فهرست نامربوط. صرف تصویب طراحی به معنی نصب، مجوز API، آزمون دسترس‌پذیری، پذیرش Product یا Release نیست.

این راهنما در **Issue/Spec/plan موجود مصرف‌کننده** ثبت می‌شود، نه Registry، workflow پذیرش، سرویس نشر یا بازبین دوم؛ انتخاب owner-approved references تنها با تصمیم همان Product است. ایجاد فرایند جدید برای پروژه‌های کوچک یا انتقال نیاز خاص یک محصول به همهٔ Tierها ممنوع است. در تغییر پروفایل منتشرشده نیز سازگاری/نسخه و تصمیم انسانی مربوط پیش از اعمال بررسی می‌شود.

## پروفایل‌های مصرف و مرز conformance

بستهٔ UI نسخه‌دار ممکن است پروفایل React، بدون React، web platform-neutral و server-rendered/WordPress-like داشته باشد. KavoshStart نباید React یا یک Provider اختصاصی، Help Center یا کل بستهٔ tests یک کتابخانهٔ بالغ را برای همهٔ مصرف‌کنندگان الزام کند. در هر محصول، **پروفایل رسمیِ موجود در نسخهٔ دقیق بستهٔ انتخاب‌شده**، root/theme/locale/RTL/asset contract و ادغام واقعی موردنیاز معیار است؛ قابلیت Help فقط اگر واقعاً انتخاب شده باشد، شواهد هم‌منبعِ همان قابلیت را می‌خواهد. تأیید upstream به‌تنهایی شاهد UI واقعی مصرف‌کننده نیست؛ و آزمایش درونی upstream در محصول دوباره اجرا نمی‌شود مگر خود integration به آن رفتار وابسته باشد.

برای کتابخانهٔ تولیدکنندهٔ UI نیز `runtime=none` و `ui.kind=none` با capabilityهای `package` و `browser-ui` قابل جمع‌اند؛ این مدل به معنی اجبار React یا تولید یک سایت مستقل نیست. تأیید مستقل کیفیت بصری، دسترس‌پذیری یا رفتار مسیر کاربر تنها در **مصرف‌کنندهٔ مجاز** و با اسناد/هویت محفوظ همان پروژه صورت می‌گیرد.
